## 🧠 Context to carry forward

The key realization of this lap: **a green `lake build PAComparator` proves almost nothing about the
comparator's trust chain.**  `Solution.lean` files declare nothing — they just `import` the
development — so Lean never checks that the challenge statement equals the development's.  That check
lives in the external `comparator` harness, which we cannot run here.  So I built a substitute:

`scratchpad/cmp/` — for each pinned name, `#check @Name` (types) and `#print Name` (bodies) under
`pp.explicit` + `pp.notation false` + `pp.fullNames`, once with the `PAComparator/*/Challenge.lean`
modules imported and once with the development's modules, then `diff`.  Notation-level churn is
erased, so a non-empty diff is a *real* divergence.  Keep using it; it is the only faithfulness
instrument available offline.  It caught three things the build was happy with:

1. **the shim vs the statement.**  The Challenge files may not import `Compat.lean`, so they must
   spell `Bounding.Hierarchy ℬ[<, ℒₒᵣ] 𝚺 1 φ`; the development was spelling the same term through
   `Compat`'s `Arithmetic.Hierarchy` abbrev, which is a *different constant*.  I restated the four
   pinned Σ₁ hypotheses on the development side.  Reasoning: `Compat.lean`'s own docstring says the
   statements are the designated audit surface and must hang off upstream directly — the abbrev
   belongs in proof internals, not in a headline.  Definitionally the same term, `AxiomCheck`
   unchanged, so this does not violate the "statements frozen" rule.
2. **pre-existing drift (namespace).**  The development had moved `base`/`bump`/`goodsteinSeq` into
   `namespace Goodstein` and typed `goodsteinSentence : ArithmeticSentence`; the comparator copy
   still said `namespace GoodsteinPA` / `Sentence ℒₒᵣ`.  Introduced by commit `00e9d60` ("Stage ε₀
   arc", staged uncompiled), i.e. *not* toolchain churn — the comparator had been quietly broken.
3. **pre-existing drift (`_proof_N` dedup)** — the subtle one.  The development consolidated
   `InternalPow → InternalLog → InternalBump → InternalGoodstein` into one `GoodsteinPA/Internal.lean`.
   Lean deduplicates the auto-generated `…_proof_N` auxiliaries of `.mkSigma` / `PR.Blueprint`
   *within a module*, so after consolidation `ibumpTableDef` reuses `ipowDef._proof_1`, whereas the
   four-file challenge support minted its own.  Same proofs, different `ConstantInfo` names →
   identity check fails.  Fix: one `PAComparator/Goodstein/Support/Internal.lean`, **in `module`
   mode** (the module system also permutes numbering *within* a declaration — non-module mode gave
   `_proof_1/_proof_2` where module mode gives `_proof_3/_proof_1`), with the defs in the
   development's order.  The development's `…construction`s and `𝚺₁-Function` instances need **not**
   be reproduced — verified empirically that they own no auxiliary proof these defs dedup onto.

Assumption I operated under: comparator compares by constant *name*, so `_proof_N` alignment matters
(this is what the old support-module docstrings asserted, and it is the conservative reading).

## ⚠️ Gotchas

* `lake build` (default targets) does **not** include `PAComparator` (deliberate: Challenge files
  carry `sorry` by design, main libs are warnings-as-errors).  Build it explicitly.
* The `sorry`s in `PAComparator/*/Challenge.lean` are the **audit surface** — they are the challenge.
  Never "fix" them.
* `set_option warningAsError false` in each Challenge file is load-bearing; removing it breaks the build.
* `lake env lean <file>` sees every olean, `lake build` only declared imports — trust `lake build`.
* Support modules are now `module`-mode; keep it that way or the `_proof_N` alignment silently breaks.
